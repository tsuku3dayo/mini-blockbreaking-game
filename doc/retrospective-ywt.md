### 2. 進め方

- 開発フロー（`doc/InputOutput_Text.txt`）に沿って、00 brief → 01 構成 → 02 要件 → 03 画面 → 04 詳細設計 → 05 テスト / 06 計画 → 07 実装 → 手動テスト → AC の順に進めた。承認のある段階では、オーナーの「承認します」まで止まった。
- 成果物はすべて ID・frontmatter（status・version・sources・verified）つきで書き、根拠（sources）をたどれるようにした。
- 07 は TASK ごとに `feat/<番号>-<内容>` → テスト名の先頭に確認 ID → 実装 → AC（draft）を同じ PR に → CI 緑 → オーナーがマージ（= GitHub Pages に公開）。WS の終わりに iPhone・パソコンで手動確認し、AC を review → 承認。
- 仕様の変更は、`doc/requests/` に記録 → 仕様書の版上げ → 承認済みの US・GUI の版上げと再承認 → TD・TC・TASK → 実装、の順で 3 回まわした。
- 次の日に続けるため、Claude Code のメモリ（project-progress）に「次にやること」を残した。
- 最後に、わかったことを開発フローに書き足し、整合性チェックを `scripts/check-docs.mjs` で自動化して CI に入れた。

### AI 駆動開発として分かったこと

- **AI にできないことがはっきりしている**：PR のマージ、作業フォルダ外の読み取り、ファイルの削除（権限で止まる）、実機での確認。これらはオーナーの作業になるので、最初から役割の表に入れておくと迷わない。
- **AI は「言われていないこと」を確かめない**：公開のタイミング（P4）、個人名（P5）は、決まり（チェックリスト）にして初めて守れた。人が暗黙に知っていることは、CLAUDE.md かフローに書く。
- **日をまたぐ作業はメモリが効いた**。ただしメモリは Claude 側にしかないので、「今どこか」はリポジトリ側にも残すほうが、人にも別の環境にも優しい。
- **AI が書くと文書が「全部そろう」が、量も増える**。そろっていることを人が全部読むのは無理なので、機械で確かめられるもの（check:docs）と、人が見るもの（要点・決めてほしいこと）を分けるのが大事。
