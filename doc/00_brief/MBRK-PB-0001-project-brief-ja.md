# プロジェクト概要（project-brief）

---

## 1. 目的

スマートフォンで手軽に遊べる、1 ステージのブロック崩しゲームを作る。あわせて、仕様書から設計・テスト・実装までを段階ごとに承認しながら進める AI 駆動開発のフロー（§7）を、小さな題材で一通り回して確かめる。

## 2. 作るもの

| 項目 | 内容 |
| --- | --- |
| 名前 | ブロック崩し（見出しは「BREAKOUT」） |
| 形 | ブラウザで動き、ホーム画面に追加できるアプリ（PWA）。サーバーなし・通信なし |
| 遊び方 | パドルを指でなぞって動かし、ボールを打ち返して 40 個のブロックを壊す。ボールを 1 回落としたら終わり |
| 主な機能 | ゲーム本体、スコア（ブロック得点 + 時間ボーナス）、端末内ハイスコアランキング（上位 10 件）、記録の書き出し・読み込み、効果音（オン / オフ設定あり）、一時停止 |
| 想定する端末 | スマートフォンの縦画面（iPhone の Safari、Android の Chrome）。パソコンの Chrome / Edge でもマウス・キーボードで遊べる |
| 詳しい仕様 | [`specification.md`](../specification.md) |

## 3. 想定する利用者

- 通勤・休憩などのすき間時間に、スマートフォンで 1〜3 分ほど遊ぶ人。
- 自分の最高記録の更新を楽しむ人（ランキングはその端末の中だけ。ほかの人とは競わない）。
- 公開 URL を開くだけで遊べ、登録やインストールは不要（インストールは任意）。

## 4. 範囲

### 4.1 含めるもの

- 仕様書 v1.1 に書かれたすべての機能。
- 単体テスト・画面テスト（E2E）と、GitHub Actions による自動確認。
- GitHub Pages への自動公開。
- README（遊び方・起動方法・ファイル構成）。

### 4.2 含めないもの

- 全プレイヤー共通のランキング、サーバー、DB、ログイン。
- 複数ステージ、残機、アイテム、BGM。
- 遊んでいる途中のゲームの保存（閉じたらタイトルから）。
- 横画面向けの専用レイアウト（横向きでは縦向きを勧める案内だけ出す）。

## 5. 前提と制約

| 区分 | 内容 |
| --- | --- |
| 構成・技術 | `simple_shogi` と同じ構成にする：Vite + TypeScript（UI フレームワークなし）+ vite-plugin-pwa + Vitest + Playwright + ESLint、Node.js 24。詳細は 01 で決める |
| 開発のルール | `simple_shogi` の `CLAUDE.md` の共通ルール（PWA の要件、保存データの扱い、デザイン、テスト、CI、ブランチ運用）に従う |
| 公開 | GitHub Pages（GitHub アカウント `tsuku3dayo`）。公開 URL は https://tsuku3dayo.github.io/mini-blockbreaking-game/ 。同じサイト（`tsuku3dayo.github.io`）にほかのアプリが載っても混ざらないよう、アプリ識別子をほかのアプリと分ける |
| 通信・個人情報 | 外部へ送信しない。名前は端末の中にだけ保存する |
| 素材 | 画像・音は自作（音はコードで合成）。外部のフォントやスクリプトに頼らない |
| 環境 | Node.js v24.0.0 と Git（Sourcetree 同梱、2.51.0）はインストール済み。リポジトリはまだ Git 管理になっていない |

## 6. 成功の基準

- 仕様書 §12 の受け入れ基準をすべて満たす（自動テストか手動テストで確認した記録がある）。
- `npm run verify`（lint → 単体テスト → build → PWA 成立チェック）と E2E が CI で通る。
- 公開 URL を iPhone と Android の実機で開き、インストール・オフライン起動・最後まで遊ぶ・登録ができる。
- 各段階の成果物がオーナーに承認されている。

## 7. 進め方

各段階の成果物は `doc/` の段階ごとのフォルダに、ID 付きの Markdown で置く。ID・ファイル名・frontmatter の決まりは [`CLAUDE.md`](../../CLAUDE.md) の「成果物の書式」に従う。「承認」の地点では、オーナーの承認を得るまで次の段階に進まない。

| 段階 | 成果物（ID の種類） | フォルダ | 承認 |
| --- | --- | --- | --- |
| 00 プロジェクト概要 | project-brief（PB） | `doc/00_brief/` | ○ |
| 01 システム構成 | system-architecture（SA）、technology-stack（TS）、architecture-decision（ADR） | `doc/01_architecture/` | ○ |
| 02 要件・ユーザーストーリー | epic（EP）、user-story（US） | `doc/02_requirements/` | ○ |
| 03 画面設計 | gui-design（GUI） | `doc/03_gui/` | ○ |
| 04 詳細設計 | technical-design（TD） | `doc/04_design/` | — |
| 05 テスト（06 と並行） | test-strategy（TST）、test-case（TC） | `doc/05_test/` | — |
| 06 作業計画（05 と並行） | workstream（WS）、implementation-task（TASK） | `doc/06_plan/` | — |
| 07 実装・自動テスト | ソースコード、自動テスト、CI | リポジトリ直下 | — |
| 手動テスト | 手動テストの結果（attested-computation に含める） | — | ○ |

**attested-computation** は、実装タスクが「実装して検証まで終えた」ことの記録である（説明は [`Attested_Computation.md`](../Attested_Computation.md)）。implementation-task（何をやるか）と test-case（どう確かめるか）に対して、「実際にやって確かめた結果」を残す。中身は、実施概要（タスク・実施者・環境）、テストケースの手順ごとの結果、**確認できなかったこと**、後片付け、完了定義のチェックリスト。Claude Code が書き、オーナーが中身を確かめて承認したら確定する（承認者と日時を記録する）。

## 9. リスクと対策

| リスク | 対策 |
| --- | --- |
| スマートフォンで 60 fps が出ない | 物理と描画を分け、描画を軽く保つ。07 の早い段階で実機で確かめる |
| タッチでの操作感（指でパドルが隠れる、発射とパドル移動の取り違え） | 落下域を指置き場にする。タップと移動を 10px で区別する（仕様書 §4.1-4）。手動テストで確かめ、必要なら値を調整する |
| iPhone で記録が消える | 記録の書き出し・読み込みを用意する（仕様書 §9.6） |
| スマートフォンで効果音が鳴らない | 最初のタップで音を使える状態にする。鳴らなくてもゲームは動くようにする |
| 古いキャッシュで起動しなくなる | `simple_shogi` と同じ起動失敗からの復旧の仕組みを入れる |
