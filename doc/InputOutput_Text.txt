工程を始めるとき・区切るときに、オーナーが出す指示。（ ）は渡すもの。
Claude Code は、指示がないまま次の工程に進まない。

00.プロジェクト概要
  開始：「仕様書をもとに project-brief を作ってください」（仕様書、対象の端末、公開先）
  区切り：「承認します」

01.システム構成
  開始：「01 システム構成を作ってください」（流用する既存プロジェクト、使いたい／使いたくない技術、公開先）
  途中：ADR で選択肢が出たら、どれにするかを答える
  区切り：「承認します」

02.要件・ユーザーストーリー
  開始：「02 要件・ユーザーストーリーを作ってください」
  途中：優先順位の付け方（段階の分け方・順位）を答える
  区切り：「承認します」

03.画面設計
  開始：「03 画面設計を作ってください」（参考にしたい画面、画面の大きさの基準となる端末）
  途中：試作の公開 URL を実機で開き、触った感想（指で隠れる・押しにくい・文字が小さい・名前が切れるなど）を返す
  区切り：「承認します」

04.詳細設計／05.テスト／06.作業計画（承認なし）
  開始：段階ごとに「実行してください」（Claude Code が「進めてよいか」を確かめたあと）
  区切り：「マージしました」

07.実装・自動テスト
  開始：「WS-<番号> を始めてください」
  区切り：PR ごとに「マージしました」

手動テスト（WS の終わり）
  開始：Claude Code が確認の手順を案内する（公開 URL、「更新」ボタンを押すこと、見てほしい点）
  返事：確認の結果（「全部 OK」、または NG の項目と様子。スクリーンショットがあれば渡す）
  区切り：AC を見て「承認します」

リリース
  開始：「リリースしてください」（バージョン番号）
  注意：リリースの PR は、マージすると公開される。公開前に入れたいもの（クレジットなど）は、この前に伝える

変更の依頼（いつでも）
  開始：変更のメモを渡す（何を・なぜ・画面のイメージ）
  途中：影響の一覧を見て、進めるか・見送るか・範囲を絞るかを答える
  区切り：版を上げた仕様書と成果物に「承認します」

  開始：「再現開発仕様書を最新にしてください」

【承認のある文書の工程（00・01・02・03、変更の依頼）】
- [ ] main を最新にし、作業ブランチを切る（docs/<工程番号>-<内容>。例：docs/02-requirements、docs/spec-1.2-control-area）
- [ ] 入力の成果物を読み、決めてほしいことがあれば、選択肢と推奨を示して先に聞く
- [ ] 成果物を status: review で書く（frontmatter：id・type・title・version・updated・sources・verified: null）
- [ ] 整合性チェックリスト（下の章）を確かめ、npm run check:docs を通す
- [ ] 03 では、試作を作って公開 URL に置き、実機で触ってもらう（下の「03 の試作」）
- [ ] コミットし、要点と決めてほしいことを短く示して承認を求め、止まる
- [ ] 承認を受けたら status: stable、verified: { by, at（+09:00） } を記入してコミット
- [ ] push して PR を作る（本文に成果物の ID・版・承認日時）
- [ ] CI が緑なのを確かめ、オーナーにマージを頼む
- [ ] マージされたら main を最新にし、作業ブランチを消す

【承認のない文書の工程（04・05・06）】
- [ ] 始める前に「進めてよいか」を確かめ、指示を受けてから作業ブランチを切る（docs/04-technical-design など）
- [ ] 成果物を書き、整合性チェックリストを確かめ、npm run check:docs を通す
- [ ] status: stable、verified: null にしてコミット → PR → CI が緑 → オーナーにマージを頼む

【07 の TASK ごと】
- [ ] main を最新にし、feat/<TASK 番号>-<内容> を切る（直しは fix/<TASK 番号>-<内容>、道具の変更は chore/<内容>）
- [ ] TASK の「やること」と対象の確認 ID を読む
- [ ] テストを書く（名前の先頭に確認 ID）→ 実装する
- [ ] npm run verify と npm run test:e2e を手元で通す
- [ ] 画面に関わる変更は、スマートフォンの幅で表示して確かめる
- [ ] 設計と違う作りにしたら、TD・GUI を直す（承認済みの GUI は再承認）
- [ ] AC（draft）を作り、自動テストの結果を書いて、同じ PR に入れる
- [ ] PR → CI が緑 → オーナーにマージを頼む（マージで公開される）

【WS の終わり】
- [ ] WS のタスクがすべてマージ・公開されたことを確かめる
- [ ] 手動テストの手順を案内する（公開 URL、「更新」を押す、端末ごとの確認項目、見てほしい点）
- [ ] 結果を受け取る（承認の言葉だけで結果がないときは、結果を先に確かめる）
- [ ] docs/ws-<番号>-ac で、各 AC に手動の結果と「確認できなかったこと」を書き、status: review にする
- [ ] 承認を受けたら stable・verified を記入 → PR → オーナーにマージを頼む
- [ ] 次の WS は、指示を受けてから始める

【リリース】
- [ ] バージョン（package.json の version）を決め、画面の表示を確かめる
- [ ] 仕様書の受け入れ基準（§12）のすべてに、確認 ID と結果があることを一覧で確かめる
- [ ] 「マージすると公開される」ことを伝え、公開前に入れたいものがないか聞いてから、マージを頼む
- [ ] 公開後に、全体の手動テストを案内する → AC を review → 承認 → PR

【変更の依頼】
- [ ] メモを doc/requests/<日付>-<内容>.md に整理する（依頼日・元のメモ・内容）
- [ ] 同じファイルに「影響の一覧」を書く（下の「変更の依頼の影響の一覧」）
- [ ] 影響の一覧を示して、進めるかをオーナーに決めてもらう（承認を受けるまで、仕様書を変えない）
- [ ] 仕様書の版を上げ、改訂履歴に書く
- [ ] 影響する承認済みの成果物を洗い出し、版を上げて status: review に戻す
- [ ] 承認 → PR（docs/spec-<版>-<内容>）

─── 整合性チェックの自動化（npm run check:docs） ───

整合性チェックリストのうち、機械的に確かめられるものを scripts/check-docs.mjs で確かめる。
文書の工程では PR の前に手元で動かす。CI の verify にも入れる。

エラー（直すまで通らない）
- ID とファイル名・フォルダが決まりどおり。ID が重複していない
- frontmatter に id・type・title・status・version・updated・sources・verified がある
- 本文・sources に書いた MBRK-<種類>-<番号> が実在する
- sources に書いた成果物の版（例：MBRK-GUI-0003（v1.2））が、相手の今の版と同じ
- status: stable の成果物の sources が、すべて stable
- 承認のある種類（PB・SA・TS・ADR・EP・US・GUI・AC）で status: stable のものは、verified が記入されている
- テストの名前に書いた確認 ID が、test-case に実在する
- test-case の確認 ID が、自動（単体・E2E）ならテストのコード（tests・e2e・scripts）に、手動なら attested-computation にある

注意（表示するだけ）
- sources の成果物に版が書いていない
- sources の仕様書の版が今の版より古い（引用した章が変わっていないか、人が確かめる）

チェックで分からないこと（人が確かめる）：文言がそろっているか、受け入れ条件と確認 ID の中身が合っているか。

作るもの
- 画面の大きさ・配置と、主な操作だけの HTML（ロジック・保存・音は作らない）
- 置き場所：prototype/ に置き、公開 URL の下（例：<公開 URL>/prototype/）で開けるようにする。07 の土台ができるまでは、手元のサーバーと同じネットワークの実機で開いてもよい

実機で確かめること
- [ ] 主な操作をしたとき、指で大事なもの（ボール・パドル・文字）が隠れない
- [ ] ボタンが押しやすい（44 px 以上）、押し間違えない間隔がある
- [ ] 小さい画面（iPhone SE 相当）でも、はみ出さず 1 画面に収まる
- [ ] ソフトウェアキーボードが出ても、画面が崩れない
- [ ] ノッチ・ホームバー・ステータスバーに内容が入り込まない（ホーム画面のアプリとして開いたときも）
- [ ] アプリの名前が、ホーム画面で切れない
- [ ] 文字が読める大きさ・色

触った結果は、gui-design の「試作での確認」に書く。直したら試作も直して、もう一度触ってもらう。
試作は 07 の実装では使わない（見た目の見本としてだけ使う）。

─── 段階ごとに先に確かめておくこと（今回の開発で、後から手戻りになったもの） ───

00.プロジェクト概要
- 仕様書に版と改訂履歴を持たせる（途中で v1.0 → v1.4 まで変わった。成果物の sources に版を書いて追えるようにする）。

01.システム構成
- 同じサイト（例：GitHub Pages の <ユーザー>.github.io）にほかのアプリも載るなら、保存のキー・キャッシュを分けるアプリ識別子を最初に決める。
- PWA にするなら、更新の切り替え方（勝手に切り替えない・「更新」ボタン）と、起動に失敗したときの復旧を決めておく。

02.要件・ユーザーストーリー
- 非機能要件（60 fps・入力の遅れなど）も、確かめ方（自動か手動か）まで書く。

03.画面設計
- スマートフォンでは、操作する指で画面が隠れないか（今回はあとから「操作空間」を足した。仕様書 v1.2）。
- ソフトウェアキーボードが出たときに画面が縮まないか、ノッチ・ホームバーの安全領域、ホーム画面のアプリとして開いたときのステータスバー。
- アプリの名前が、ホーム画面で切れない長さか。

04.詳細設計
- Canvas の中身は E2E から読めないので、状態を見る・変えるテスト用の入口（?debug=1、body の data 属性、イベント）を設計に入れる。
- ロジック（ルール・物理）は DOM・時刻・乱数に触れない作りにし、単体テストで確かめる。

05.テスト
- test-case の番号は user-story と同じにする。非機能のテストケースを途中の番号に置くと、あとから足したストーリーと番号がずれる（今回：US-0022 → TC-0023、US-0023 → TC-0024）。非機能は最後の番号にまとめるか、番号の決まりを最初に決めておく。
- E2E は CI（Linux）と手元でフォントが違う。文字の幅に頼るテストは書かない。
- 実機でしか分からない項目（iPhone の Safari・ホーム画面のアプリ・音・VoiceOver など）を、手動のテストケースとして先に一覧にする。

06.作業計画
- epic の優先順位どおりに WS を並べる。最初の WS は土台（CI・公開・PWA の骨組み）にする。
- attested-computation の番号は TASK と同じにする。仕様の変更で足した WS は、表で実施の順を示す（今回：WS-0009 を WS-0006 と WS-0007 の間に実施）。

07.実装・自動テスト
- PR の前に、手元で verify（lint・単体テスト・build・dist の検査）と E2E を通す。画面の変更は、スマートフォンの幅で表示して確かめる。

手動テスト
- 確認の手順と、見てほしい点をこちらから案内してから、結果をもらう。結果をもらう前に「承認します」と来たときは、結果を先に確かめる。
- 持っていない端末（今回は Android）は、確認できなかったことに理由と一緒に書く。


─── 運用の注意 ───

- 承認はチャットの「承認します」「OK」で受ける。はっきりしない返事のときは確かめる。
- PR のマージはオーナーが行う。main へのマージで公開されるので、リリースに関わる PR は「マージ = 公開」と伝えてから頼む。
- 実機がない端末（例：Android）は、attested-computation の「確認できなかったこと」に書く。
- 了承をとっていない人の名前は、公開リポジトリに書かない。
