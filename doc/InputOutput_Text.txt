00.プロジェクト概要
- 仕様書に版と改訂履歴を持たせる（途中で v1.0 → v1.4 まで変わった。成果物の sources に版を書いて追えるようにする）。

01.システム構成
- 同じサイト（例：GitHub Pages の <ユーザー>.github.io）にほかのアプリも載るなら、保存のキー・キャッシュを分けるアプリ識別子を最初に決める。
- PWA にするなら、更新の切り替え方（勝手に切り替えない・「更新」ボタン）と、起動に失敗したときの復旧を決めておく。

02.要件・ユーザーストーリー
- 非機能要件（60 fps・入力の遅れなど）も、確かめ方（自動か手動か）まで書く。

03.画面設計
- スマートフォンでは、操作する指で画面が隠れないか（今回はあとから「操作空間」を足した。仕様書 v1.2）。
- ソフトウェアキーボードが出たときに画面が縮まないか、ノッチ・ホームバーの安全領域、ホーム画面のアプリとして開いたときのステータスバー。
- アプリの名前が、ホーム画面で切れない長さか。

04.詳細設計
- Canvas の中身は E2E から読めないので、状態を見る・変えるテスト用の入口（?debug=1、body の data 属性、イベント）を設計に入れる。
- ロジック（ルール・物理）は DOM・時刻・乱数に触れない作りにし、単体テストで確かめる。

05.テスト
- test-case の番号は user-story と同じにする。非機能のテストケースを途中の番号に置くと、あとから足したストーリーと番号がずれる（今回：US-0022 → TC-0023、US-0023 → TC-0024）。非機能は最後の番号にまとめるか、番号の決まりを最初に決めておく。
- E2E は CI（Linux）と手元でフォントが違う。文字の幅に頼るテストは書かない。
- 実機でしか分からない項目（iPhone の Safari・ホーム画面のアプリ・音・VoiceOver など）を、手動のテストケースとして先に一覧にする。

06.作業計画
- epic の優先順位どおりに WS を並べる。最初の WS は土台（CI・公開・PWA の骨組み）にする。
- attested-computation の番号は TASK と同じにする。仕様の変更で足した WS は、表で実施の順を示す（今回：WS-0009 を WS-0006 と WS-0007 の間に実施）。

07.実装・自動テスト
- PR の前に、手元で verify（lint・単体テスト・build・dist の検査）と E2E を通す。画面の変更は、スマートフォンの幅で表示して確かめる。

手動テスト
- 確認の手順と、見てほしい点をこちらから案内してから、結果をもらう。結果をもらう前に「承認します」と来たときは、結果を先に確かめる。
- 持っていない端末（今回は Android）は、確認できなかったことに理由と一緒に書く。


─── 運用の注意 ───

- 承認はチャットの「承認します」「OK」で受ける。はっきりしない返事のときは確かめる。
- PR のマージはオーナーが行う。main へのマージで公開されるので、リリースに関わる PR は「マージ = 公開」と伝えてから頼む。
- 実機がない端末（例：Android）は、attested-computation の「確認できなかったこと」に書く。
- 了承をとっていない人の名前は、公開リポジトリに書かない。
