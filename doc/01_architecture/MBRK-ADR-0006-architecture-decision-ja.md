# ADR-0006 保存は localStorage、バックアップは記録の一覧を書き出す形にする

## 状況

保存するのは記録 10 件・数個の設定値だけで小さい。仕様書 §9.5 は、登録の保存に失敗したら「保存できませんでした」を出して再度押せることを求めている。§9.6 は、読み込むファイルの記録を 1 件ずつ検証し、別のアプリ・新しすぎる版・壊れたファイルを理由つきで断ることを求めている。

`simple_shogi` の `storage.ts` は、書き込みに失敗しても何も返さない（失敗を画面に出さない作り）。バックアップは、アプリの保存キーの中身をそのまま書き出している。

## 決定

- 保存は `localStorage`。`simple_shogi` と同じく、読み書きを `try/catch` で包み、キーはアプリ識別子で始め、版番号（`schema`）と移行（`migrate()`）を持つ。
- **書き込みは成否を返す**ようにする。登録では失敗を画面に出す。設定（効果音）の保存は失敗しても無視する。
- 登録では、記録一覧・次の id・前回の名前・自分の記録 id を書き込む。途中で失敗したら、書き込んだ分を元に戻し、登録を失敗とする（記録だけ入って id がずれる状態を作らない）。
- バックアップは仕様書 §9.6 の形（`app`、`schemaVersion`、`scores` などの項目）で書き出し、読み込み時にロジック層で 1 件ずつ検証する。効果音の設定は含めない。
- 起動時に `navigator.storage.persist()` で、保存データを消されにくくするよう頼む（`simple_shogi` と同じ）。

## 検討した選択肢

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| **A. localStorage + 成否を返す（採用）** | 小さなデータに十分。同期で扱いやすい。`simple_shogi` の作りを流用できる | 容量が小さい（このアプリには十分） |
| B. IndexedDB | 容量が大きい。トランザクションがある | 非同期で、このデータ量には過剰 |
| C. simple_shogi と同じく保存キーをそのまま書き出す | 流用だけで済む | 記録ごとの検証（§9.6）がしにくい。改ざんされたスコアを見つけにくい |

## 結果

- 良い点：仕様書の失敗時の動きとバックアップの検証を満たせる。
- 注意点：`simple_shogi` の `storage.ts`・`backup.ts` はそのままでは使えないので、土台を流用して直す。
